# Сценарий показа демо (5–7 минут)

Шпаргалка для докладчика: что открыть, что запустить, что увидит зал, что сказать и почему это работает.
Архитектура: [architecture_java.md](architecture_java.md). Правила для агента: [AGENTS.md](AGENTS.md).

**Одна мысль, которую должен унести зал:** сгенерированный тест не знает, что такое «правильно». Правильное берётся из спецификации, а доверие к тестам измеряется mutation score, покрытием требований и defect escape rate, а не числом тестов и line coverage.

---

## 0. Термины за минуту

| Термин | Что это | Где в репо |
|---|---|---|
| **Оракул** | Источник ожидаемого результата теста: «что должно получиться». Если оракул — код, тест повторяет код вместе с его багами | `openspec/specs/**/spec.md` |
| **Сценарий** | `GIVEN / WHEN / THEN` с ID в заголовке (`TXT-EQ-01`). THEN — это и есть ожидаемое значение для assert | спеки, `#### Scenario:` |
| **Тест из кода** | Агенту дали реализацию и попросили «100% покрытия». Он записывает в assert то, что код *делает* | `src/test/java/demo/fromcode/` |
| **Тест из спеки** | Агенту дали только сценарии и сигнатуры. Он записывает в assert то, что код *должен* делать | `src/test/java/demo/fromspec/` |
| **Gate 1** | `openspec validate --strict`: у каждого требования есть сценарий, дельта оформлена правильно | job `gate-1-spec` |
| **Мутант** | Копия кода с одной мелкой порчей: `>=` → `>`, `return x` → `return true`, условие инвертировано | генерирует PIT |
| **Убитый / выживший мутант** | Убит, если хотя бы один тест упал на испорченном коде. Выжил, если все тесты остались зелёными: эту порчу тесты не замечают | `target/pit-reports/` |
| **Mutation score** | Убитые / все мутанты. Показывает, *проверяют* ли тесты поведение, а не просто *выполняют* ли код | job `gate-2-mutation` |
| **Gate 2** | Сборка падает, если mutation score ниже порога (`pit.mutationThreshold` = 80) | `pom.xml` |
| **Покрытие требований** | Сценарии, у которых есть тест с их ID / все сценарии | `scripts/req_coverage.py`, job `req-coverage` |
| **Defect escape rate** | Дефекты, найденные в проде / все найденные дефекты за период. Арбитр: если он растёт, зелёные гейты врут | `metrics/escaped_defects.csv` |
| **Line coverage** | Доля строк, которые хоть раз выполнились в тестах. Ничего не говорит о проверках: строку можно выполнить и ничего не проверить | JaCoCo |

## 1. Подготовка (накануне)

```bash
git clone git@github.com:sMichellin/demo_boost_sdd.git && cd demo_boost_sdd
git fetch --all --tags
```

- [ ] JDK 17 + Maven 3.9, либо podman с образом `docker.io/library/maven:3.9-eclipse-temurin-17` (см. README). Прогреть кеш: `mvn -B test` на `main`, чтобы на сцене Maven ничего не скачивал.
- [ ] `openspec --version` (1.13+).
- [ ] Открыть PR из `demo/c` и `demo/e` в `main` (не мержить): на сцене показываем готовые красные проверки, а не ждём CI.
- [ ] Прогнать бенчмарк заранее (около 4 минут на два набора) и держать вывод в терминале: на сцене его не запускать.
- [ ] Записать диалог агента для `demo/d` (шаг 5 ниже): это запись, а не живой прогон, модель может ответить по-разному.
- [ ] Вкладки браузера: PR из `demo/c`, PR из `demo/e`, PR на `main` с комментарием-отчётом, страница ruleset `main: quality gates`.

Запасной вариант на любой шаг: `git checkout step-NN` открывает состояние репозитория после шага N (таблица тегов в README).

## 2. Показ

### Шаг 1. Тест из кода защищает баг (сценарий A, слайд 3) — 1 мин

```bash
git checkout demo/a-b
sed -n '8,12p' src/main/java/demo/text/TextUtils.java      # equalsIgnoreCase
mvn -B test -Pdemo-from-code
```

**Зал видит:** `Tests run: 6, Failures: 0`, `BUILD SUCCESS`. В тесте есть `assertTrue(TextUtils.equals("ABC", "abc"))`.

**Сказать:** «Агент написал тесты по коду, CI зелёный, покрытие 100%. И баг теперь записан в тест как норма: кто его починит, тот сломает сборку».

**Почему так:** оракулом для этих тестов был сам код. Тест, который сверяет код с самим собой, не может найти расхождение с намерением.

### Шаг 2. Тест из спеки ловит баг (сценарий B, слайд 9) — 1 мин

```bash
sed -n '/TXT-EQ-01/,/false/p' openspec/specs/text-equality/spec.md
mvn -B test
```

**Зал видит:** `Tests run: 6, Failures: 2`:
- `TXT-EQ-01 different case is not equal`: `expected: <false> but was: <true>`
- `AUTH-LOCK-01 lockout on sixth attempt`: `expected: <LOCKED> but was: <SUCCESS>`

**Сказать:** «Тот же код, тот же агент. Разница только во входе: вместо реализации мы дали сценарии. Оракул пришёл из спецификации, и оба внесённых дефекта найдены».

**Почему так:** ожидаемое значение взято из строки THEN, которую написал человек. Код с ней не совпал, тест упал. Каждый тест помечен `@Tag("<ID сценария>")`, поэтому падение сразу указывает на требование.

### Шаг 3. Требование без сценария не проходит CI (сценарий C, слайд 10) — 1 мин

```bash
git checkout demo/c
cat openspec/changes/broken-no-scenario/specs/auth-lockout/spec.md
openspec validate --all --strict --no-interactive
```

**Зал видит:** `MODIFIED "Account lockout" must include at least one scenario`, во вкладке PR красный `gate-1-spec`, кнопка Merge заблокирована ruleset'ом.

**Сказать:** «Требование без сценария — это требование без оракула. Из него нельзя сгенерировать проверяемый тест, поэтому оно не проходит в `main` уже на уровне спеки, до всякого кода».

**Почему так:** Gate 1 проверяет структуру: `SHALL/MUST` и минимум один `#### Scenario`. Проверка обязательная (ruleset `main: quality gates`), обойти её «под честное слово» нельзя.

### Шаг 4. Mutation-гейт отсекает тесты-пустышки (сценарий E, слайды 14–15) — 1 мин

> Порядок как в архитектуре: E показываем перед D, потому что D — запись.

```bash
git checkout demo/e
sed -n '/void loginServiceDoesNotThrow/,/^    }/p' src/test/java/demo/fromspec/WeakCoverageTest.java
mvn -B test org.pitest:pitest-maven:mutationCoverage
python3 scripts/quality_report.py
```

**Зал видит:** тесты зелёные, покрытие требований 100% (теги на месте), line coverage 100%, но `Mutation score of 6 is below threshold of 80`, Gate 2 красный.

**Сказать:** «Это тесты, которые выполняют каждую строку и ничего не проверяют. Покрытие строк 100%, покрытие требований 100%, все зелёные. Ловит их только мутационный тест: мы портим код 18 способами, а тесты замечают 1 порчу из 18».

**Почему так:** line coverage считает *выполненные* строки, покрытие требований считает *наличие* теста с ID. Обе метрики можно накрутить. Mutation score считает *замеченные изменения поведения*, его без настоящих assert не накрутить.

### Шаг 5. Агент находит неоднозначность (сценарий D, слайд 11) — 1 мин, запись

```bash
git checkout demo/d
sed -n '/AUTH-LOCK-03/,$p' openspec/changes/add-lockout-reset/specs/auth-lockout/spec.md
```

Сценарий: `WHEN some time has passed / THEN the user can usually log in again`. Запись: агенту дают промпт из [prompts/generate-from-spec.md](prompts/generate-from-spec.md). По правилу из `AGENTS.md` он **не пишет тест**, а спрашивает: сколько именно времени, что значит «usually», отсчитывать время от блокировки или от последней попытки.

**Сказать:** «`validate --strict` здесь зелёный: структура в порядке. Неоднозначность смысла видит только тот, кто пытается превратить THEN в assert. Агент с правилом “не угадывай” останавливается до кода, и спеку правит человек».

**Почему так:** из «usually» нельзя получить `assertEquals`. Агент без такого правила угадал бы значение (например, 15 минут) и записал свою догадку как требование.

### Шаг 6. Бенчмарк на своих дефектах (сценарий F, слайды 15, 19) — 1 мин, готовый вывод

```bash
git checkout main
scripts/benchmark.sh                     # from-spec
scripts/benchmark.sh --suite from-code   # from-code
```

**Зал видит:** `from-spec: caught 8 of 10` и `from-code: caught 2 of 10`, плюс построчно, какой дефект каким тестом пойман (разбор в разделе 3).

**Сказать:** «Мы взяли 10 своих же дефектов, по одному вернули их в код и посмотрели, какой набор тестов заметит. Тесты из спеки поймали 8, тесты из кода поймали 2. И главный баг из шага 1 тесты из кода как раз *не* ловят».

### Шаг 7. Отчёт о качестве вместо «N passed» (сценарий G, слайды 14, 17) — 30 сек

Вкладка любого PR в `main`: комментарий бота «Отчёт о качестве».

**Сказать:** «Вот что мы показываем вместо “3000 passed”: три метрики сверху, а line coverage и число тестов внизу с пометкой “не является аргументом”».

## 3. Как читать замер

В README записано:

> Замер на `main` (maven:3.9-eclipse-temurin-17): mutation score 94% (17/18), покрытие требований 100% (6/6), бенчмарк `from-spec: caught 8 of 10`, `from-code: caught 2 of 10`.

Разбор по частям.

**`maven:3.9-eclipse-temurin-17`** — где измерено: в контейнере с Maven 3.9 и JDK 17 (сборка Eclipse Temurin). Те же версии стоят в CI (`setup-java` temurin 17), поэтому локальные цифры совпадают с цифрами в PR.

**Mutation score 94% (17/18).** PIT сделал 18 мутантов из `TextUtils` и `LoginService`, тесты из спеки убили 17. Выжил один: `LoginService.isLocked` подменён на «всегда `true`». Ни один сценарий не утверждает, что аккаунт *не* заблокирован (например, после 4 неудач), поэтому никакой тест этого не проверяет. Это пробел спеки, а не ошибка генерации: лечится сценарием вида «GIVEN 4 failed logins THEN the account is not locked», после чего агент сгенерирует тест и score станет 100%. Порог 80% пройден с запасом.

**Покрытие требований 100% (6/6).** В `openspec/specs` шесть сценариев (`TXT-EQ-01..04`, `AUTH-LOCK-01..02`), у каждого есть тест с `@Tag` того же ID. Метрика отвечает только на вопрос «у каждого ли требования есть тест». Хороший ли это тест, она не знает: на `demo/e` пустышки дают те же 100%. Поэтому она идёт в паре с mutation score.

**Бенчмарк `from-spec: caught 8 of 10`.** В `benchmark/defects/` 10 патчей, каждый возвращает в код один правдоподобный дефект ([defects.csv](benchmark/defects.csv)). Скрипт по очереди накладывает патч на чистую копию `main` и прогоняет набор тестов. Дефект «пойман», если упал тест, который на чистом `main` проходит. Пропущены два:
- `D05-trim-before-compare` (пробелы по краям игнорируются);
- `D08-password-case-insensitive` (пароль сравнивается без учёта регистра).

Ни для того, ни для другого в спеке нет сценария. Тесты из спеки ловят ровно то, что в спеке написано. Оба промаха — пробелы спецификации, их видно по колонке `requirement_id = (no scenario)`.

**Бенчмарк `from-code: caught 2 of 10`.** Набор из кода поймал `D02` и `D03` (обработка `null`) и пропустил остальное, в том числе `D01-equals-ignore-case`, тот самый баг, который он закрепил в шаге 1. Чтобы сравнение не прозвучало сильнее, чем оно есть: набор из кода покрывает только `TextUtils` (так задано в архитектуре, шаг 5). Пять дефектов в `LoginService` он не мог поймать в принципе. На своей территории (`TextUtils`, D01–D05) счёт 2 из 5 против 4 из 5 у тестов из спеки, и промах на D01 — главный.

**«Числа зависят от модели и промпта».** Тесты в этом репозитории написаны одной моделью по промптам из [prompts/](prompts/). Другая модель или другой промпт напишут другие assert: могут добавить проверку `isLocked == false` и убить последнего мутанта, а могут пропустить проверку счётчика и потерять D06. Выборка маленькая: один мутант — это 5,5 п.п. score, один дефект — 10 п.п. бенчмарка. Дефекты и спеку писал один и тот же автор. Поэтому со сцены переносится **способ** (спека как оракул, мутанты, свои дефекты как бенчмарк), а не проценты. Повторить замер на своём коде: `mvn -B test-compile org.pitest:pitest-maven:mutationCoverage` и `scripts/benchmark.sh`.

## 4. Если что-то пошло не так

| Проблема | Что делать |
|---|---|
| Maven начал качать зависимости | Переключиться на вкладку PR с готовыми проверками, локальный прогон показать после доклада |
| Нет сети | Все шаги, кроме вкладок PR, работают офлайн при прогретом кеше `~/.m2` |
| Не та ветка или грязное дерево | `git stash -u && git checkout <ветка>` |
| Вопрос «а если тесты из кода покрывают всё?» | Раздел 3, абзац про from-code: на своей территории 2 из 5 против 4 из 5, и главный баг пропущен |
| Вопрос «а 94% — это много?» | Важнее, что выжило: один мутант, и он показывает недостающий сценарий. Score — повод открыть отчёт PIT, а не оценка |
